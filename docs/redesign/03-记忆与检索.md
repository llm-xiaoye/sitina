## 二、事件、事实和指令

Journal 是经历权威，记录“谁在什么版本下观察、执行或声称了什么”。模型自述、用户猜测和未经核实结果仍是 claim。审核通过的经验只代表在给定证据、范围和版本下被接受，不能证明永远正确。

普通经验召回使用已审核且当前适用的版本。主动历史查询可以读原始事件、失败尝试、旧计划和争议证据，但明确标注来源、状态和适用性，不能自动作为当前事实。

Memory body 是数据，不能升级为系统指令。Skill 说明通过能力加载通道使用；新强制规则通过独立批准通道生效。普通经验、能力说明和权限规则不能相互悄悄转换。

### 审核经验对任务的生效边界

新任务保存 memory_view_ref 和实际采用的记忆 ID／版本。任务结束后新增的审核经验默认对后续新任务生效；活动任务不被后台静默更换方法依据。当前用户纠正立即按任务输入处理；已确认错误、撤销或隔离的旧条目在下一次相关行动前停止作为事实，必要时重查受影响结论。固定视图不是继续相信错误的理由。

当前 B6 接线将原始 `memory_view_ref`／版本集作为不可变任务边界；原条目被 native authority 撤销后，任务不会改写原 CAS 或注入后来无关经验。实际用户 `CORRECTION` 先进入任务输入，再以原视图身份重新取证并持久记录排除项；上下文历史 reader 读取有 proof/hash 的 revalidation CAS，重开后按同一来源恢复有效视图。UNKNOWN effect 继续阻止无依据成功，持久 `next_due_at` 在重开和 claim 边界都先检查，未到期义务不派发。以上是已接入且有本地证据的边界，不等于模型提取内容质量或新任务收益已验收。

### B7 终态经验输入证据与适用条件

B7 的提取和独立审核共用一份由真实终态历史重放得到的 `input_evidence`。它必须绑定原 task/session、run/epoch、goal／acceptance 版本、终态 Envelope 身份及 `handled_input_seq`，按 Journal 的原序列逐条读取原 CAS body，核对 body 引用、哈希、task/input/kind 身份，并排除终态之后或尚未处理的输入。任一缺失、错序、身份／哈希不符或超预算都在 Provider 派发前停靠，保留可追溯错误，发送计数为零。

候选审核的来源读取／原生审核绑定也必须处于持久化前检协议内。证据缺失、不可读、格式／身份错误或超预算且尚未发送时，以 candidate/revision/source closure/request/attempt 绑定的处置记录原因、exact send=0、not_sent 与 next_due_at。当前首版复用候选处理最多三次的总预算；该计数不是 Provider 发送次数，物理发送事实另外保存。前两次 NEEDS_WORK，到期后可续接，第三次 FAILED_FINAL 并结清该候选；所有候选明确处置后才 SETTLED 父义务。审核身份包含候选尝试序号，同一 Host 请求 stem 不造成不同尝试身份冲突。未到 due 不再读取或派发，重开继承状态。写入这些处置本身失败仍传播并 fence，不能伪造持久成功。

投影上限为 128 条、单条正文 16 KiB、总量 48 KiB。原始 goal 是目标基线；已处理 `MESSAGE`／`CORRECTION` 是本任务语义输入；`PAUSE`／`CANCEL`／`STATUS` 等只作为 control-only 记录，不自动成为长期偏好。候选可带 task-specific 或 reusable 适用范围；task-specific 条件不得为空，且要保留在最终可召回的 memory 正文或既有字段中。候选可以用空的 `evidence_input_sequences` 表示仅依据原 goal 与实际终态结果；一旦引用序列，必须来自已核实的语义输入，不能引用控制、未来或不存在的记录。

这组规则约束来源、范围和可追溯性，并不宣称模型绝不会泛化；不支持的普遍规则仍由独立审核拒绝或要求补证。既有 source closure、CAS 哈希、历史 manifest 和不含这些可选字段的旧候选保持原样可读，新增投影不回写旧历史。当前两次真实 Native memory 内容边界审计支持“本任务限定条件保留”和“过度泛化候选拒绝”；它不等同于完整新任务收益或完整首版验收。

原始历史仍可按需查询，返回时标明历史证据身份。下一任务可以在上一个任务的经验尚未整理完时开始，使用已可用的视图并如实显示整理状态；不能为了等待经验而阻止所有新任务。

## 四、结项后的异步经验整理

**异步结项整理是本版必需合同，取代旧稿“禁止异步整合”。** 异步指与用户任务交付解耦，由同一后台按到期时间及可配置处理名额调度；不能只等所有业务空闲，否则长任务可能令经验长期不生效。无需引入复杂队列平台，见 00 R09。

1. 成功、最终失败或取消以唯一已提交的 TaskTerminated 事件作为终态和应生成的 episode、整理及交付义务的共同来源。
2. 待办是终态事件的可重建投影；启动及后台处理根据该事件确定地补建缺失义务，不在提交终态后仅向内存排队。
3. 按终态事件身份和处理版本去重，重启或重试不重复发布同一逻辑结果。
4. episode 保存事实经历、结果和来源，不把提取者的猜测写成已证实结论。
5. 完整提取后先持久提交包含稳定 candidate_id、内容和来源引用的清单，再逐项独立审核；执行冲突、去重、替代和归档规则，单条处置与发布同时持久记录。
6. 清单提交前的提取故障按 R09 续接或重做尚未完成提取；清单已提交后的审核／发布故障只处理未结清候选，保存原因、计数与重试入口；单条明确拒绝或无需经验可以不发布而结清该条。父义务须完整清单内每条都有最终处置才完成，有效空清单可直接完成。拒绝后重提须有修订和新依据，不能无限重生成同一候选。任务结果不因此失去已完成状态，更不能重新执行用户任务。

暂停、等待和卡住仍保留任务状态，不急于形成最终结论。用户后来明确取消或最终失败时再生成结项义务。候选在处理中不会导致当前事实集不唯一：普通检索只读已提交的审核版本，候选状态和处理版本都持久记录。

Journal 写入和状态提交仍由单机后台统一协调。冲突检测与语义提取不放在每次 append 的热路径，不用内存 pending 假装可靠排队。

### 一次提取多条经验的恢复与结算

父义务身份继续来自终态事件、义务类型和 processor_version。保存 batch_id、来源范围、提取请求／版本及完整清单引用，单条候选另有 candidate_id 和修订。完整清单提交前不发布流式候选；中断的部分响应不等于空清单。提交后回执丢失先读回原清单，不另生成另一组条目。

例如 A 已发布、B 明确拒绝、C 审核超时，父义务显示“发布 1／拒绝 1／待处理 1”，仍未完成；恢复只重试 C，不能重跑业务或重复 A、B。争议未决／需要处理仍属未完成；隔离本身不算结清。最后一条处置提交后，父状态可由清单和逐项决议直接重建。新依据要重提已拒绝候选时记录关联修订，已完成父义务后的新提取另建有理由的关联义务。精确合同见 00 R09。

## 五、经验身份与冲突

`conflict_key` 表示“关于什么的断言”，不等同于事件 ID。例如项目测试命令、实际入口、工具错误与目标位置。程序根据规范化字段及候选内容形成稳定键；语义映射保留理由和来源，不让模型直接宣称自己 authoritative。

```text
test_command:project_a
entrypoint:code_mode
error_key:str_replace:no_match:core/sitina/cli.py
```

键包含适用项目、主题和必要版本；临时路径归一化，仓库内保留有意义的相对路径。缺少足够身份信息的候选继续 pending，不能用随机新键绕过冲突。

冲突追加 `ConflictDetected` 指向相关事件或记忆，不修改历史。相互冲突且尚未查明的候选隔离；不能因为后写就胜出。必要时重新读取代码、配置、工具实际结果；无法判断则保留 disputed，不进入普通召回。

事实冲突与用户改目标分开处理。用户纠偏更新当前有效目标；旧工具结果只证明其观察时的状态，不能覆盖新的用户要求。客观事实按当前来源、内容、版本与可重复观察判断，不采用笼统的“工具永远高于用户”排序。

### 审核期间发生更正时如何发布

候选与审核回执引用来源版本及有关 conflict_key 的当前版本。提交时通过既有持久写入口复核：相关事实未变才采用原审核；不相关变更不阻断；相关变化只重做受影响的冲突和适用性核对。未查明就保持 disputed，不允许迟到审核重新启用已撤销经验。

发布、替代和单条 candidate_id 的最终处置由同一个持久记忆决议事件表达；父义务依据完整清单和逐项结果确定重建。它复用已有条件提交，不建立新数据库、第二个任务写入口或跨审核的长锁。具体规则见 00 R09。

## 六、schema 与可恢复投影

首版应有 `schema_version`。保留实际个人场景需要的 project/session/task/agent 标识；稳定 task_id 与每次 run_instance_id 分开，不能把重启当作新用户任务。

```yaml
schema_version: 1
memory_type: semantic | episodic | procedural_candidate
project_id:
session_id:
task_id:
run_instance_id:
agent_id:
conflict_key:
status: candidate | accepted | disputed | quarantined | superseded | retired
source_event_ids: []
source_trust:
scope:
version:
valid_from:
expires_at:
review_due_at:
supersedes: []
superseded_by:
review_policy_hash:
review_receipt_refs: []
```

source_trust 和发布状态由程序依据实际证据及审核合同写入，提取者只提交候选。审核依据需可追溯；字段齐全不是事实真实的证明。

历史事件不改写；物化视图可以被当前版本重建。兼容新增字段可读时填默认值，破坏性变更需明确读者和投影迁移策略，不能为省事悄悄解释旧字段为新含义。

数据密钥必须可在重启后受控重新取得。读取历史数据与建立新执行身份分离；进程内密钥不能支撑首版恢复承诺。

## 七、episode 和会话边界

一个 task 表示一次完整用户任务；一个持久会话可以包含多个关联任务，也可以跨 REPL 重连。每次运行实例是执行身份，不是任务本身。

活动任务的纠偏更新有效版本并继续任务。状态询问不创建目标版本。任务成功后追加新工作建立关联 task 和 episode，复用适用背景，原终态不重新打开。最终失败与取消也保留经历及结项处理义务。

## 八、长期经验审核与积累治理

候选由提取者提出，由非提取者独立审核；程序发布审核结果。核实的失败原因可以保留，不把一次环境故障或一次替换失败泛化成永久禁止。

| 动作 | 作用 |
|---|---|
| 去重／合并 | 相同适用范围和结论增加来源，避免多条重复提醒。 |
| 替代 | 环境或做法改变时发布新版本，旧条目标 superseded。 |
| 失效／隔离 | 过时、冲突或无法核实的经验退出普通检索。 |
| 归档 | 详细历史移出日常有效集，必要时仍能查询依据。 |
| 更正／撤销 | 用户可纠正事实或撤回偏好；保留变更来源。 |

历史物理数据可以增长，不能承诺磁盘永不增长；有效召回和单轮上下文必须有界。TTL/review_due 可辅助发现过时条目，不能仅因时间到了就自动删除仍必要的证据。

衡量记忆不是条数，而是相同或相关新任务能否少走已验证的死路、正确使用项目约束，并在环境改变时重新核实。

## 九、working state 与 checkpoint

工作状态是事件驱动、可重建投影。可从最近已验证任务根对象或投影快照加后续事件恢复，不强制每轮从事件 0 重放，也不要求仅有旧存储 checkpoint 字段就能重建新任务。

失败摘要和阻碍索引跨压缩保留；详细失败尝试存储可查询。未完成操作的状态、资源归属、能力版本与验收差距是恢复必要部分，不只保存一条 summary。

投影损坏可重建；原始提交失败必须停下依赖该状态的新动作。恢复时核对实际环境与操作效果，不能用存储回放假定文件、外部安装或旧进程仍保持原状。

## 十、检索安排

| 层 | 首版／后续 |
|---|---|
| 当前任务投影、近期结果和证据索引 | 首版承担连续性。 |
| 结构化历史查询 | 首版按任务、项目、错误、路径、操作和验收项查实际记录。 |
| 相关已审核经验 | 首版按项目、适用范围和问题选择，必要时由助手主动查询。 |
| episode 相似检索、其他可重建索引 | 后续按真实检索缺口增加，不是首版记忆的前置条件。 |

```text
sitina journal query --error-key <key> --limit 5
sitina journal query --task-id <id> --phase verify
sitina journal query --path <path> --exit-code nonzero
```

命令是拟提供接口，不表示当前 CLI 已接新任务模型。返回条目有状态、来源与读取入口；工具输出限制大小，超过范围给可续查游标或更精确过滤。

精确查询擅长已知身份，不宣称严格优于所有相似或全文需求。首版不要求向量数据库；后续索引必须可重建，删除索引不改变权威事件和审核记忆。

## 十一、结项经验与长期规则

运行中利用反馈纠正本任务；任务结束后再提炼跨任务经验。**没有“某错误第三次出现就立刻停下审批”的规则，也不自动把四次无进展升级为永久禁止。** 复发次数是证据之一，不是置信度或发布开关。

稳定、可核实且有通用价值的做法可以提出 procedural 候选。新强制规则必须说明来源、适用范围、预期收益和误拦风险，由用户批准后对新任务生效；活动任务继续记录其当前规则版本。

```yaml
rule_id: reread_before_retrying_changed_file
source_error_key: str_replace:no_match:<project_path>
source_event_ids: []
source_task_ids: []
status: proposed | approved | retired
scope:
version:
condition:
action:
trigger_count: 0
last_triggered:
```

优先可审阅的声明式规则；确需代码检查时走正常开发与相关验收。规则独立版本管理，可撤回，可记录误拦；高触发次数不自动禁用，也不自动证明有效。自动批量生成和迭代 Skill 属于后续能力，不阻首版经验系统。

## 十二、归档与 GC

复用 CAS 去重与 GC 的相关基础；保留 accepted 经验及恢复所需的来源闭包。可按存储大小触发归档，默认阈值仅是可调配置，不等于删除历史证据的授权。

区分从 prompt 移除、从普通检索排除、归档、真正删除。真正删除先留下必要 tombstone，并确保未完成任务、审核、交付和恢复不再依赖对象。优先修复任务 scratch 和进程生命周期，不能把用户成果或在途操作当残留清掉。

## 十三、功能验收

- 长任务经历多次上下文整理后仍满足原目标、最新纠偏与未完成义务，不重复已经核实的失败方法。
- 关闭窗口后台继续；进程退出后使用新执行身份恢复原任务及可查询证据。
- 成功、最终失败、取消与后处理排队之间中断，恢复不漏 episode 或整理义务，也不重复执行用户任务。
- 新任务使用适用审核经验得到实际帮助；环境变化或错误记忆能触发重新取证、隔离或替代。
- 整理失败不阻已经满足交付的任务，不发布未审核内容；历史增长不导致单轮上下文无界增长。
- 任务 A 的经验在任务 B 运行期间发布：B 不被静默换依据，之后的新任务 C 可使用；旧经验被撤销时 B 也停止依赖。
- 两个同主题候选审核交错并遇到用户更正，迟到审核不能重新发布错误版本；无经验／拒绝可结清。
- 持续存在用户任务时，到期整理仍有调度机会，失败只重试未完成部分，不重跑业务。
- 三条候选分别发布、拒绝、超时，中途重启保留已处置项，只处理剩余候选；清单提取中断不当作空清单，最后一条已结清可重建父完成状态。

这些检查验证记忆的正确作用；错误记忆注入只是其中一个样例，不是唯一验收。正式实现路径和评分器按 [04](04-实施步骤.md)、[07](07-基准规范.md) 接入本版规则。
