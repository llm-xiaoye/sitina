## 总原则

先建立真实任务基线，再接通新 Loop，完成首版记忆、后台连续性与真实能力使用，最后退役旧路径。采用 strangler：新路径 → 有界切流 → 实际验收 → 冻结旧路径 → 删除。不能把行数下降、模块存在、依赖安装完成当成功。

第一至第三步共同交付首版。记忆、长期任务、关闭窗口后台继续、同机同版本恢复和 Skill 安装后真实使用不能被移到“以后优化”。并行候选写入、computer use、自动找活与任意跨天监测属于后续范围。

每个里程碑有一项前置检查：**当前改造路径和对应评分器是否对本批涉及的规则采用 00 的同一语义，并如实记录尚未覆盖的部分。** 不允许新 Runtime 允许只读完成，而旧评分器仍要求非空 diff；不允许循环仍在第三轮或隐藏默认总轮数处停止。只更新文档或配置项不满足接线要求。每批列 target_spec_version、implemented_rules、verified_rules、unimplemented_items；已接入未验证的差集单列。相同规范版本下只通过部分案例不等于完整合同通过，也不能以分批为由继续执行相反旧规则。

## 批次和停靠

一个批次围绕明确目标、依赖边界和允许范围；记录当前源码、配置、工具版本及工作区初态。commit 或内容哈希清单都可固定身份，不要求无差别 `git add -A`，不覆盖用户原有修改。

正常调查、修复和相关验证在已授权范围推进。用户要求的阶段停靠继续遵守；需要改变用户目标、超出已有授权或确实缺少用户信息时再询问。报告包含已完成部分、明确阻碍、推荐理由和各选项利弊。

同一障碍四次有意义尝试无进展时保存并报告；评审分歧三次、暂时故障重试另计。发现相关回归先定位和修复，不能宣布里程碑通过；不能用重命名 batch 或 attempt 绕开计数。

以当前内容版本审查，漂移后只重建受影响证据。先做最小必要检查，再跑正式产品场景及与本次合同直接相关的故障恢复，最后完成必要回归；不附加通用安全攻击测试流程，也不在没有新问题时机械反复全量测试。
