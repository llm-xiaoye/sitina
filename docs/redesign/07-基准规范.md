## 一、目标与基本区分

首先验证用户真实任务能完成、错误能修正、长期循环不失去目标、重启可继续、记忆能帮助新任务。组件绿色、工具已注册、Provider 连通或保护性拒绝都不能替代正式 CLI 的产品结果。

日常任务验收和 Sitina 版本验收分别记录：日常修改／安装完成前有一个独立评审；版本基准使用程序检查和两个非主循环评审。记忆审核是结项后处理，不是第三张完成票，也不是每轮三模型投票。

Runtime 和评分器共享同一任务合同与状态语义，只在评审人数等明示项目上不同。运行记录和基准结果包含 spec_version，混用版本不得生成可比较通过分数。相关接线是 [04](04-实施步骤.md) 每个里程碑的前置要求。规范版本不表示覆盖已完整：trial 另附 target_spec_version、implemented_rules、verified_rules 及 unimplemented_items，并列已接入但未验证的差集；verified_rules 引用当前实现／入口证据。案例行为 PASS 仅证明该案例覆盖的义务，完整首版 PASS 须全部必需规则验收；混用相反旧语义仍不合格。

## 二、少量真实任务起步，逐步分组

| 套件 | 用途与规则 |
|---|---|
| 回归 | 已稳定完成的真实任务；出现相关回归不能宣布新版本通过，应修复或明确尚未满足。 |
| 能力 | 用户想完成、尚未稳定做成的任务；记录实际成功与阻碍，稳定后加入回归。 |
| 保留集 | 未用于本轮调参的独立任务，逐步扩充，在预先约定的版本决策时使用。 |

首步不要求冻结 30–45 个案例或用户独自标注。实现者根据真实任务准备输入、初态和预期结果，用户重点判断任务是否真实、成果是否满足需要。

初始用例至少能代表代码修改验证、只读调查审查、长试错，以及获取并实际使用第三方 Skill。长期任务与记忆不是等案例规模扩大后的可选增强。

保留集不能一边调参一边反复偷看。若根据其失败改了设计，该案例可转入开发／回归范围，下一轮独立性另行说明；不再宣称仍是未见样本。

## 三、case schema

通用字段描述结果义务，代码测试字段只在适用案例中出现。

```yaml
spec_version: sitina-loop-v1-r4
case_id: install-and-use-skill-001
suite: capability
kind: capability_install
goal: <真实用户要求>
initial_state_ref: <目录、依赖、注册状态和必要记忆的可复现记录>
expected_task_state: SUCCEEDED
required_outcomes:
  - id: discover_and_use
    result: 当前任务或指定验证会话从真实 Sitina 入口显式使用候选并产生符合要求的成果
    evidence: 候选快照、稳定位置与依赖、实际调用及最小有效用例结果
  - id: publish_default
    result: 候选真实试用通过后才成为普通新会话的默认版本
    evidence: 有效试用引用、publication_id、完整快照及预期原默认发布身份的条件提交
  - id: new_session
    result: 不指定候选的普通新会话仍能实际使用本次发布
    evidence: 实际默认发布身份、加载与调用结果、成果内容检查
delivery:
  location: <用户要求的最终消费或成果位置>
allowed_effects: <本案例允许的项目与安装位置>
forbidden_effects: <不可改变的用户内容及固定评分依据>
initial_memory_ref: <本案例允许使用的审核记忆版本>
notes: <实施者核实的考点与检查依据>
```

适用代码案例可附 repo_snapshot_ref、expected_paths、forbidden_paths、test_command、expected_counts 和行为断言；它们不能成为所有 case 的必填项。初态可以包含 unborn Git、未提交／untracked 内容或已有基线错误。

对只读结论、文档和图形成果，明确内容标准与适用证据。对“现状已满足”，允许无修改。对正确询问或取消案例，评分可以判行为正确，但 expected_task_state 不能假写成功。

必要验收方法的实质变化属于版本变化；不得将“新会话实际使用”偷换成“读取安装日志”。测试中的 Sitina 不得自己降低固定评分要求。

## 四、评分器

```text
程序：核对规范版本、案例初态和当前成果身份
   → 按任务类型逐项执行或读取适用证据
   → 检查必要操作、交付义务与资源归属
   → 适用内容评审：两个非主循环模型独立检查
   → 输出 CASE_PASS / CASE_FAIL / NEEDS_REVIEW 等分类
   → 同时记录实际 task 状态和完整 trial 结果
```

CASE_PASS 与任务 SUCCEEDED 不是同一个字段。例如“缺少必要输入时正确询问”的案例可以通过，实际任务仍是等待输入。

### 程序检查

- 按当前任务合同检查，无统一 diff 非空或必须跑测试要求。
- 代码案例核对行为、真实执行、范围和必要测试计数；不只比较 exit 0。
- 安装案例核对完整候选经真实消费者入口试用后才条件发布默认，证据对应 publication_id、快照和预期原默认；再核对普通新会话未指定候选仍实际加载本次发布，调用和最终成果有效。仅构建成功不足以发布，候选试用失败或未知不得进入默认。
- 无修改案例核对足够依据；只读任务按来源和结论判断。
- 评审与检查结果绑定目标、验收、成果版本和已处理输入位置，旧结果不能批准新合同。
- 任务临时资源在不再需要后清理；用户成果、原有文件、待完成受管进程不能当残留删除。

### 四例参考成果校准

复用一个小 CSV：time_s 为 0、10、20、30；concentration_mg_L 为 0、25、50、75。共同要求是时间—浓度折线图，横轴 s，纵轴 g/L，正确数值为 0、0.025、0.05、0.075；配色不作硬要求。参考材料见[r4 校准包](/Users/moss/Documents/ChatGPT/sitinaRedesign/r4-review-calibration-2026-09-06/README.md)。这是确定性参考夹具，不是 Sitina 或真实评审已通过的记录。

| 校准对象 | 参考判断 |
|---|---|
| 数值、单位、来源、呈现均满足要求 | 通过。 |
| 漂亮图形把 mg/L 数值直接标成 g/L | 阻断并指出换算错误，不能凭外观过门。 |
| 数据和含义正确，仅采用另一种配色 | 通过；额外风格建议不能变成必须修项。 |
| 图可看但缺少可核实数据来源／转换依据 | 缺证据，申请补证或取证；不提交成功，也不武断认定数字错误。 |

程序核对实际绘图数据、单位、输入与输出依据，模型读取真实制品及任务关系。参考图不能作为逐像素唯一答案。每例分别记录程序检查、每位评审、整体门的判断和证据，并标记误放行／误阻断／未决；没运行的评审记 NOT_RUN，不能因为程序挡住错误就给评审算一条正确。

单独校准评审时只交各例中性审查包与共同要求，参考标签及其他案例答案不提供给被测模型。程序挡住的例子可以额外让既有评审独立读包以观察其判断，这只属于校准，不能反过来覆盖实际程序失败。不增加评审人数，也不以四例推断普遍误判率；真实人工语义分歧再请用户处理。

### 双模型面板

两个非主循环评审读取同一冻结对象、原始要求和证据，各自判断。机器可直接确认的失败不能被投票覆盖；双方均无阻断且其他条件满足才通过。分歧或超时为 NEEDS_REVIEW，不静默使用剩余一票。

保留全部 trial 数量、结果与原因。分歧、超时和证据缺口不能通过从报告中消失来抬高成功率；若报告有效评分子集，必须同时报告总尝试、排除原因和未决数量。

日常只有一个独立评审，评审内容分歧三次处理；暂时服务故障独立重试。首版临时故障默认初次失败后最多两次重试，可按调用配置调整，精确规则见 00；它不是用户四次无进展的延伸。

## 五、评分依据与用户内容

固定评分夹具和隐藏判据不得由被测 Agent 修改。程序在实际执行范围落实这一点，不能只靠 prompt。

这不意味着日常所有测试文件都不可修改。新增或修正项目测试可以是用户任务的一部分；需要与不可改写的独立评分依据区分。不能删失败检查、降低断言或更换目标使评分虚假变绿。

隔离 fixture 只重置其获授权内容。真实用户目录的原有修改不可被清理；包含未提交或 untracked 的案例应显式声明预期初态，不能被“必须全干净”规则排除。

## 六、失败和阻碍归因

记录原始命令、环境、返回状态、输出、实际影响及基线，然后区分：任务未完成、任务造成的失败、外部环境阻碍、等待输入、等待评审、用户控制或效果未知。

不得仅凭特定 pytest exit code 宣布环境错误并从分母排除。收集、导入或配置错误可能由当前改动引入；测试未执行也不能按“环境问题”跳过必要验收。已知无关基线问题单列并解释，不一律阻断也不隐藏当前引入的失败。

一次初态失效的 trial 可标环境无效，但总报告仍列出该次及原因；修复环境后的重跑是另一条记录。外部因素与产品无法处理该因素的缺陷分别说明。

## 七、主指标与诊断

主指标是**真实完成、稳定性、必要人工接管与耗时**。报告对应任务类型和条件，不把 token 消耗作为选择更低完成率方案的理由。

每个 trial 记录：

- 目标结果与各验收项，实际 task 状态，评分状态和理由。
- 人工接管／等待用户的次数、原因和是否确有必要。
- 总耗时、有效执行、工具等待和评审等待。
- 工具与模型调用、token、主循环及子任务轮数。
- 同一障碍尝试、策略变化、评审分歧和临时故障，分别计数。
- 实际模型、代码、配置、依赖、Skill／能力快照和初始记忆版本。
- 安装案例的候选试用、默认发布身份与原默认、普通新会话实际选择；发生确认回归时的隔离和条件撤回／停用结果。
- 完成提案与实际证据的冲突，成果和证据可读回入口。

工具先后顺序可用于诊断，不作为所有任务固定标准。已有足够成果时允许直接申请检查；不为显示 search-first 或 100+ 轮而制造调用。无需记录内部思维链。

`sitina-termination-v1` 另记录批次归还原因、成功但重复的动作／证据、进度振荡、稳定复查问题与格式／读取／服务分类、停止报告可读回，以及正常探索被误停的样例。指标用于定位，不按轮数或费用自动降低验收与模型。报告明确哪些计数由程序事件直接得到、哪些仅为模型解释。

同进程重建 Backend、文件存在、PID 消失、单次 exit 0 或无状态 mock 均不足以证明跨进程恢复。确定性替身测试须明确标注；少量真实 CLI 案例在冻结源码和已有持久密钥下执行。报告如实区分声明范围通过、未覆盖工具、T5 CONTRACT_ONLY 与完整首版未完成。失败尝试和不确定发送仍留在证据中。

## 八、执行纪律

| 项 | 规则 |
|---|---|
| 初态 | 按案例冻结目录、依赖、必要外部状态和初始记忆；不默认强制所有案例干净 Git。 |
| 重复试验 | 记录实际成功次数与重复条件；一次 trial 内允许正常多轮返工。 |
| 任务内计数 | 同一障碍四次有效尝试，与外部 trial 次数、三次评审分歧和临时重试分别计算。 |
| 普通试验隔离 | 不继承上次产物或记忆，除非案例明确要求。 |
| 记忆收益试验 | 明确共享哪些审核经验，比较适用任务的重复试错、完成和环境变化处理。 |
| 报告 | 全部尝试与分类可对账，不用少量样本宣称普遍可靠。 |
| 调试 | 先看真实失败与评分器是否误判，按影响补充检查，避免重复全套测试。 |

回归要求稳定，不用 pass@k 的偶然一次成功掩盖已知失败；能力用例可以报告多次尝试中的成功，但必须保留尝试总量。没有样本依据时不制造统计承诺。

## 九、首版必需场景

| 场景 | 正常完成形状 | 相关故障或边界 |
|---|---|---|
| 修改并验证代码 | 行为实现、相关检查、独立评审及实际成果 | 模型自述完成但检查失败必须返工；unborn／未提交内容保留。 |
| 只读调查／无需修改 | 来源和结论符合问题，无 diff 仍可完成 | 缺证据不得假装确定；正确询问仍保留待完成任务。 |
| 安装并使用 Skill | 获取和部署完整候选，真实入口显式试用，通过后条件发布，普通新会话默认调用及成果正确 | 首次试用失败不发布；确认回归后的隔离和条件撤回见下表；旧调用继续绑定旧快照。 |
| 长任务与纠偏 | 多次压缩仍保留义务，依据新信息继续 | 评审中改要求、成功提交前暂停，旧证据不得通过新状态。 |
| 无进展处理 | 正常调查超过四次工具调用仍继续 | 同一障碍四次有效尝试停靠；批次不能无限追加重复读取。 |
| 后台与恢复 | 关终端继续，重新连接看到同一 task | 程序重启、新执行身份、旧实例不能提交；长操作到期重判。 |
| 操作效果未知 | 核实后接纳已完成结果或续接部分成果 | 效果前／部分发生后／完成未落记录时中断，不盲目重发。 |
| 共享资源 | 不同会话扩展登记均保留 | 旧 generation 不能覆盖别人更新，恢复不能提前释放占用。 |
| 经验与记忆 | 结项后整理，新任务真实受益 | 终态可补建义务；拒绝／无经验可结清；错误经验隔离与替代。 |
| 交付 | 最终使用位置有效且任务要求满足 | 可选通知失败只补通知，必要交付未完成不能报成功。 |

正常路径与必要故障检查成对证明本版承诺，不另设通用攻击测试项目。代码案例的真实 diff、测试计数、Reviewer 和成功终态仍有价值，只是其中一种形状，不能推广给只读与安装任务。

### R07 的候选与默认发布场景

这些场景随能力安装接线验证，复用已有任务、会话、登记和版本目录，不新增多助手并行候选平台。

| 场景 | 正确表现 |
|---|---|
| 构建成功但首次真实调用失败或未知 | 原默认和旧运行条件保持；原来无默认则仍未启用。修复形成新快照后重验，不用旧成功证据批准新内容。 |
| 候选试用中取消，或重启后收到迟到结果 | 取消后不因迟到通过发布；仅重启则恢复核实试用、控制状态和发布身份，当前条件成立方可按合同继续。未知试用按 R08 核实，不重开已取消的业务任务。 |
| 试用通过、条件发布并由普通新会话使用 | 发布绑定有效试用和预期原默认，同次记录普通新会话检查义务；新会话不显式选候选，证据对应实际选中的 publication_id 与快照。后来版本的结果不得算作本次发布通过。 |
| 发布后确认自身依赖、绑定或接口回归 | 先按 publication_id 持久隔离并登记处理义务；当前默认仍为本次发布且旧环境可用时，以新 publication_id 恢复旧快照，不倒拨旧身份。 |
| 确认回归但无旧版本或旧运行条件已失效 | 去掉仍属于本次发布的坏默认，以新变更身份记录空默认，明确能力暂不可用并保留修复入口。 |
| 回归处理前已有后来发布，即使版本名相同 | 不覆盖或按同名版本连带隔离后来发布；原发布处理记录为被后续发布取代。扩大隔离必须另有相应证据和适用性依据。 |
| 输入不适合、缺凭据或外部服务暂时故障 | 处理当前调用条件，不直接判能力回归或撤回健康默认；未通过候选仍没有发布资格。 |
| 发布回执丢失，或发布检查／归因／撤回中取消或重启 | 按发布身份重读，恢复普通新会话检查、待归因及默认处理义务，不重复发布、不丢隔离、不盲目恢复旧表；单纯取消业务目标不自动撤回健康安装，也不重开已取消的业务任务。 |

检查最小用例不能绕开真实 Sitina 消费者；单独脚本、import、文件存在或登记成功均不能替代候选实际使用。试用通过只是发布资格，整项任务仍须满足全部成果要求、必要独立评审和交付。

### r3 的跨模块衔接场景

| 场景 | 正确表现 |
|---|---|
| 原任务试用 C、发布 P，普通新会话确认 P 回归 | 原任务下一次受影响调用也核对 P；不能换回候选身份绕过隔离；无依据不影响后来发布 Q。 |
| 任务 A 稳定等待用户，B 修改另一项目 | A 保存现场并释放可释放占用；B 推进；A 恢复核对期间变化。A 尚有未知本地写入时先核实，不能假释放。 |

| 两个同主题候选审核交错，并有用户更正 | 发布核对相关记忆版本；迟到审核不重启已撤销事实，发布／替代／义务结果可一致重建。 |

### r4 的定向接续场景

| 场景 | 必须观察到的结果 |

| 提取中断或有效完整空清单 | 部分结果不误判为空；完整有效空清单可以结清无需经验。 |
| A 发布、B 拒绝、C 超时，处理中重启 | 已完成处置保留，只处理剩余候选；C 需要处理时父义务未完成。 |
| 最后一条候选处置提交后父汇总未写 | 从完整清单及逐项决议重建父完成，不再提取或发布。 |
| 批次 1b 只验证短任务 | 覆盖表准确，恢复／记忆未实现不得列已验证；规范版本不授予完整首版 PASS。 |

上述场景随对应实现批次执行，规则与 00 相同；本次文档修订未运行它们。
