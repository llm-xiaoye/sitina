### 输入先入日志，结果再按归属使用

1. 窗口发送 `input_id` 和目标任务，后台用该 ID 去重，持久化后才返回“已接收”。读取进度也是输入，但解释后不必改变目标版本。
2. 明确暂停或取消立即更新控制意图。普通文本待解释期间，不派发新的业务写入，也不提交成功；已启动操作按 R04 处理。必要的只读调查和输入解释可以继续。
3. 一个模型请求开始时绑定当时的任务版本。模型返回后、工具真正派发前再核对。若期间收到尚未处理的新输入，先处理它，不能直接执行旧工具调用。
4. 迟到结果始终保留原始归属。它可以证明某个旧操作实际发生过，但不能只按 `task_id` 给当前验收标通过。
5. 未受变化影响的旧证据可以复用：另写适用性记录，说明当前条目、成果和检查覆盖为何仍匹配，保留原证据身份。不得改写旧结果使其看似属于新版本。

### 完成有一个明确的提交点

首版采用一个本地后台协调器串行处理输入和任务状态；模型与工具可以在外计算，状态提交全部回到此入口。不是在检查时持锁等待模型，而是在结果返回后做短的条件提交。

以下为需要实现的逻辑合同，不代表现有方法名：

```text
处理完成申请(proposal):
  在同一状态处理段读取当前任务
  要求该 task_id 尚未提交逻辑终态
  要求后台持有当前执行权，proposal 的预期版本仍适用
  要求 received_input_seq == handled_input_seq
  要求 control_intent 允许完成
  要求当前必需验收条目有有效证据
  要求必要评审没有阻断或未解决证据缺口
  要求影响成果的操作已明确结束或完成约定的资源交接
  要求最终使用位置与必需交付已验证
  要求成果及原始证据已持久保存
  以 expected_stream_version 条件提交一个 TaskTerminated 事件
  该事件同时描述终态、最终成果和后处理义务
  持久提交成功后，才向窗口发布成功
```

用户输入的持久追加与这次提交使用同一串行入口及预期日志版本。输入先提交，完成申请就必须重查；完成先提交，随后收到的追加工作建立关联新任务。保证的是后台已接收事件的顺序，不是假定尚未送达后台的键盘输入已经生效。

提交冲突时重新读状态并处理受影响事项，不能自动重放“成功写入”。日志写失败时停止新副作用并显示保存故障，不能先宣布成功再补日志。底层现有去重和预期流版本检查可复用，但还要实现上述业务条件。

同一 `task_id` 只有一个逻辑终态位置，成功、最终失败与取消争用该位置。终态命令使用稳定的去重身份；提交回执丢失时先读取该位置，已有终态就返回原事件和成果，没有才重新核对并提交。不能因为换了请求 ID 再生成第二个终态或第二组经验义务。任务结束后的新工作建立关联任务。

对文件与外部环境的验证是有时间和对象范围的：对 Sitina 管理的写入通过 R05 保持一致；用户或第三方直接修改不受内部锁约束。提交前复核相关内容，已检测变化就作废相关证据；持久保存获验收的成果内容身份和观察时点。不得承诺可以原子锁定任意外部网站或用户编辑器，也不得把可变路径说成永久通过的成果。

## R03 · 重启后的第一步与执行身份

### 数据可读与有权执行是两件事

新的持久任务存储需要保存 Journal 验证、CAS 解密等数据密钥的稳定引用，并保留可信的历史签发者公钥及关联记录。密钥材料保存在本地 Keychain 等已有持久密钥机制中，不写入普通日志。必须在首次业务副作用前完成持久化和重新读取验证。

历史签名验证身份仅证明旧记录来自谁；它不能恢复旧进程的活跃执行许可。新后台取得单机排他所有权后，建立新 `run_instance_id`，为接续任务提交新的 `execution_epoch` 和当前授权范围。存储签名或认证身份的接续需要明确的持久信任起点，不能用一个新随机公钥覆盖旧 pin。

恢复入口只能查询已有密钥。找不到密钥时不得调用“缺失即生成”来冒充旧 key ID。现有 InMemory 密钥已经丢失的遗留目录不承诺无损恢复；保留原资料，能独立检查的外部成果重新取证，并明确这是新建可验证起点，不能伪造旧历史。

### 恢复顺序

1. CLI 优先连接已运行后台；启动新后台时取得同一存储根的 OS 排他锁。另一个有效后台仍在运行，则连接它或报告占用，不启动第二个写入者。
2. 打开稳定任务目录，查询已有数据密钥和历史验证身份，验证日志已提交范围及所需成果。密钥不可访问或验证失败进入 `RECOVERY_BLOCKED`。
3. 从已验证任务投影检查点和其后的提交事件重建状态。投影带 `schema_version`、`reducer_version`、`source_frontier`；版本不支持则停止接续写入，不能跳过不认识的义务。
4. 恢复原始与新增输入、当前目标和验收、证据状态、进展计数、待审对象、操作、能力版本、交付及经验义务。缺失投影可重建；四字段 TurnCheckpoint 不足以提供这些信息。
5. 建立新执行代次，但先保留所有未解决资源占用，核实旧进程和 R08 中的未知效果。代次只能拒绝旧状态提交，不能让已启动的 shell 自动停止写文件。
6. 重新确认工作目录、依赖与能力绑定。完成已收到但未解释的输入；用户原有暂停或取消意图优先保留。
7. 写入 `RecoveryReady` 后才允许继续业务动作。依次恢复到运行、等待具体操作、暂停或明确阻碍；不把模型对话重新开始当成一个新用户任务。

Keychain 暂不可访问时等待其恢复，不丢任务；确实缺钥时报告哪些历史无法读，推荐基于外部成果重新核实的选择及限制。旧执行者无法确认时，不释放其资源并重发相同操作。

跨版本迁移、跨机器恢复仍属后续。首版必须验证“同机同版本、全新进程”接续，不能只在同一个 Python 进程内重建对象来代替。

### 2026-09-08：C1—C8 连续性接入合同

以下细化 R03/R04/R05/R08，标识 `continuity_contract_version=sitina-continuity-v1`。它界定本批恢复所需的持久事实与验证行为；事件名称可以按现有代码组织，但不能省去相应提交边界。当前状态见批次 3 实施计划，不因本段存在宣称已接线。

2026-09-08 的 3B 语义细化：显式启动后台可自动接续具有完整兼容描述、已确认安全且原控制意图为 RUN 的任务；status/attach 不启动后台或接续。显式 resume 先持久受理有稳定幂等身份的有序继续意图，再由执行器处理；它只能覆盖更早 PAUSE，不能覆盖更晚 PAUSE 或任何 CANCEL，不修改目标/验收。纯恢复不默默解除暂停，取消和终态不重开。恢复验证不长期占用控制请求锁；Ready 提交与后续派发均复核当前输入前沿。按各任务保存的结构化环境身份验证，不能将启动后台时的另一个 workspace 当成任务环境。已持久的 cycle、preflight、检查/评审、私有协议引用及待处理输入按安全边界重建；不能仅放开旧执行身份断言后从 cycle=0 重跑。

一个后台可以保守串行派发任务的业务修改；控制处理不得被长业务调用或不完整客户端请求无限阻塞。后台停止使用明确排空或忙碌出口，不能为了退出而伪造用户暂停/取消。宿主线程、执行器和进程包装是五模块内的实现，不新增常驻模型角色。

## R04 · 进程属于任务，等待不触发退出清理

管理进程的对象由后台任务执行器持有，不由一次模型调用或一次 Forge attempt 的局部 `finally` 决定存活。模型调用结束只释放该调用自己的资源；窗口断开不结束任务。

| 状态或事件 | 已启动操作如何处理 | 何时释放写入权 |
|---|---|---|
| `WAITING_OPERATION` / 等待评审 | 保留操作身份、输出和完成事件，继续等待实际结果 | 操作确认结束、其效果已登记之后 |
| 窗口关闭 | 后台按原任务继续 | 不因窗口关闭释放 |
| `PAUSING` | 不派发新业务动作；按工具合同请求正常停止，或等待不能安全打断的操作到达明确结束点 | 确认不再写入、保存部分结果后 |
| `PAUSED` | 不自动继续；持久保存恢复入口 | 已静止资源可以释放；恢复前重新核对现场 |
| `CANCELLING` | 不派发新业务动作，停止经核实属于本任务的操作，核对已经发生的效果 | 不能仅因发出停止信号就释放 |
| 成功或最终失败 | 清理本任务拥有且应停止的临时资源；保留成果、证据与明确交付资源 | 各项操作静止或完成明确交接后 |
| 用户要求留下运行服务 | 验证服务后登记保留归属、状态、日志与停止入口 | 转交为受管理的服务资源；不能只是无人管理的 keep 标记 |
| 后台退出或机器重启 | 按 R03、R08 核实旧进程与效果 | 未核实的写入者仍占用对应资源 |

首版不承诺冻结并原样恢复任意进程的内存。暂停可以是保存进度、停止操作，之后按该工具的恢复合同继续。界面必须区分“已请求暂停”和“已暂停”。取消不自动回滚已发生的结果。

每个长操作保存 `task_id`、`operation_id`、启动实例/代次、PID 与进程组、可核对的启动身份、命令与工作位置、能力版本、允许输出、日志和结果位置、停止办法。不能只靠 PID 存在判断归属，PID 不在也不能推断未执行或成功。

首版可增加薄的命令执行包装层：输出直接落到任务日志文件，正常结束时将带操作身份和退出码的结果写入专属临时文件再替换为完整结果。结果文件只是待验证观察，正式任务状态仍由协调器登记。避免依赖随父进程消失的日志排空线程；即便结果文件缺失，仍走效果核实，不能推导退出码。

当前 `process_start/status/log/cleanup` 会核对整个工作区差异并可能停止与回滚。这条路径不能原样用于允许产生产物的安装或构建。新接口须按声明的输出范围记录合法变化；发现范围外变化先比较归属，不把用户期间修改或其他合法变化一律回滚。

如果取消后仍有无法确认的外部效果，保存未解决义务与资源占用，明确显示结果未知。对可能仍在写入的本地进程保持 `CANCELLING/RECOVERY_BLOCKED`；不能宣称所有进程已停止。需要用户决定时按已约定的完成部分、阻碍、利弊和推荐格式说明。

## R05 · 哪个任务可以写共享资源

首版采用一个单机后台状态写入口和统一业务写入队列。只读调查、模型计算可并行；不为高并发设计多机协调。文件锁保护后台唯一性及必须支持的独立入口事务，所有写入入口遵守相同资源身份和版本规则。

资源身份由实际解析后的路径或环境/登记 ID 确定，目录包含关系也算冲突；不是简单比较用户输入的路径字符串。不同副本只有其独立目录不冲突，共用的扩展和依赖仍是共享资源。

| 资源 | 持有范围与提交方式 |
|---|---|
| 项目目录或副本 | 一个任务在修改执行段内持有该工作范围；交付或静止、保存现场后的稳定交接可释放，恢复重新取得范围并核对期间变化；其他任务在交接前等待或使用副本，不能每次工具返回就交错改同一成果 |
| 单个异步操作的输出与依赖环境 | 从派发到确认静止一直占用；返回 WAITING 不释放 |
| 扩展版本内容 | 本操作专属 staging 准备；完整验证后发布不可变版本，已发布版本不原地改写 |
| 共享登记表 | 同一协调入口串行核对共享能力流的当前状态与预期版本，提交权威决议，再推进 registry 投影；generation 由权威位置派生，不能独立自增决定默认，见 R07 |
| 共享依赖环境 | 安装与升级期间独占；有活动使用者时等待其结束，或使用独立版本环境，不在运行中原地替换依赖 |
| 有效项目记忆 | 提取可以并行计算；审核后的发布、替代与冲突处理经同一持久写入口 |

个人首版可以先串行执行所有业务修改，不要求不同资源同时写入；资源归属记录仍必须存在，以处理等待、恢复与释放。登记表这类短事务不用持有到整个任务结束，项目目录这类持续成果不能每个工具调用后随意转给另一个任务。

登记请求表达本次意图，例如“将 Skill A 的默认从 X 改为 Y”，而不是提交早先读出的整张表。协调入口先读到共享能力流的已提交位置，再按同一能力的预期发布身份核对；其他能力变化可合并，同一能力改变则重新判断。权威提交成功以 R07 的 Journal 决议为准；投影写失败不能假称提交未发生，异常先查原决议。

CLI 的安装、禁用、回滚，后台安装及经验发布均使用同一入口。只改新 Loop、留下旧 CLI 直接写表不算完成迁移。当前查到的旧会话清理锁不能被当成扩展登记锁。

内部锁不能锁住用户编辑器。普通目录修改与副本应用前后仍核对相关原始内容、用户未提交与未跟踪文件；冲突时保存差异并重新判断。释放锁不等于撤销操作，代次更新不等于旧子进程已停。

### r3：首版写入调度的具体选择

采用一个全局业务修改通道，同一时刻由一个任务的修改执行段占有。一个执行段从获准产生效果开始，到没有在途写入、相关效果已核实并保存现场为止；可以包含若干工具和模型步骤，不等于单次文件写，也不把整个长期任务永久占住通道。独立任务的只读调查和模型计算可以并行。任务记录的短提交始终通过唯一状态入口，与长操作的修改通道分开。

- 可以立即记录 WAITING_INPUT 或 STALLED、报告阻碍并接收用户判断，不以证明静止为前提；稳定 PAUSED 仍遵守 R04。只有释放修改通道和相关资源前，必须确认写入静止、核实效果并保存成果身份；未确认时保留占用及停止／探测入口。静止后其他任务可推进。任务的工作目录、候选和证据仍保留；恢复可以先初查，但必须在重新取得通道及资源归属后，最后核对相关内容、环境和操作前提，再决定是否派发；不能用排队前的核对或旧基线批准写入。
- 下载、构建或效果未知的本地写入尚在运行时，仍保留相应占用及修改通道。停止、探测和必要收尾有优先调度入口，不排在被它们解除的普通业务之后。等待界面显示具体占用任务和操作；不能假称已静止。
- 每个已结算批次检查排队工作。有其他可推进修改时，在可静止边界保存并让出通道；不会为了切换而杀掉有进展的命令。首版接受长写命令期间其他业务修改排队，不引入跨资源并发写调度器。
- 不在持有一部分长期资源时等待另一任务持有的资源：取得通道后登记本执行段全部已知范围；新增范围不可取得时先静止、保存并释放可释放占用，再整体重试取得。无法释放的在途效果先处理，不让另一业务修改进入形成互等。注册表等短锁不能跨模型或工具等待持有。
- 原任务请求的检查与普通新会话验收是它的验证操作，保留独立会话和被检查版本，但共享其资源归属，不在等待验收的父任务后排队。验证操作只拥有声明的检查效果范围。
- 取消后的发布核实、效果探测和默认修复以 obligation_id 调度，只执行必要收尾；不能被“原业务已取消”一概拦截，也不重开被取消的用户任务。

这个保守调度是本轮工程起点，不是用户曾要求全局只能有一个任务。未来允许不重叠资源并行修改时，只替换调度策略，保留任务、效果、资源和提交合同。

### r4：取得写入权之后的最后核对

排队前的读取仅为准备材料。程序取得通道与所需资源归属后，记录当前执行段及归属版本，重读本动作所依赖的文件内容／存在状态、环境与能力身份、命令前提，再复核 R02 的执行权、有效输入和目标／验收版本。确认仍适用后持久登记该操作的写前依据才可派发；派发时它必须仍属于当前执行段，已让出的归属不能被旧模型结果继续使用。

相关前提改变就停止旧动作直接写入，返回差异给主助手重新读取、调整或重新验证；确实不受影响的操作可以附适用性依据复用，不机械作废所有计划。不能给旧结果换一个新执行段编号就当重新核对。对延迟启动的工具，执行器也检查所携带的当前归属；已经派发但尚未启动也属于未结清操作，确认撤销启动或结束前不能当作空闲释放；开始写后一直保留该范围到效果核实。读取文件和等待模型不持有状态提交锁，读完后的登记与派发再次核对 R02 条件。

此规则关闭 Sitina 受协调写入之间的空档，不声称锁住用户编辑器或任意外部进程。文件编辑工具在实际应用处核对期望原内容；不支持条件写入的长命令明确依赖范围、保留占用并核对结果。发现外部变化保存冲突，不整目录覆盖。检查只覆盖本操作的相关前提，不为每个工具全库重算哈希。

## R06 · 评审请求检查的执行合同

评审可以读成果，也可以向程序提出检查请求；不能因请求名称为“检查”就继承主助手的全部执行范围。复用已有工具与执行隔离能力，不新增逐项审批系统。

请求至少包含：验收条目和方法版本、成果/环境引用、检查命令或读取内容、工作位置、输入范围、允许写入的临时位置、必要网络与子进程能力、超时与停止方式、预期证据类型。程序根据已授权任务和可用执行配置核对并登记；不能只相信请求方自称只读。

| 检查类型 | 执行范围 | 结果与失败出口 |
|---|---|---|
| 读取检查 | 当前成果与证据只读；无业务写入 | 返回实际内容及版本；来源变化则更新对象 |
| 本地运行检查 | 源成果只读，缓存、输出和临时数据库写检查专属区域；网络默认不需要，确有需求按任务范围配置 | 项目测试必须在源码旁写文件时，用包含当前实际内容的副本；不能随意放开原目录 |
| 实际消费者检查 | 验证最终 Sitina 入口、依赖与新会话；允许事先声明的会话记录、缓存和测试产物等运行副作用 | 记录实际影响；需要扩大任务范围或缺少凭据时，交主助手按原有授权规则处理 |

子进程、网络和文件范围在执行前具体确定。现有某个 worker 的 Seatbelt 配置不能自动代表所有 shell/MCP 路径都满足合同；无法承载某项检查的执行器应报告具体缺口，不能退回不受控命令执行。

执行前记录待检对象；执行后核对相关内容变化。预期临时输出不改变业务成果版本；源文件、安装状态等实质变化会使受影响证据失效。需要修改真实方案时，由主助手在写入合同下完成，再重新检查。固定基准夹具与评分标准不能由被测对象修改；日常任务按用户范围处理项目测试文件，不一概禁止合理测试修复。

为了使检查通过而改变启用版本、安装位置、依赖或业务配置属于修复，不能由评审以“检查”名义完成。需要可写测试配置时放在检查专属环境，并记录它与最终消费环境的差异；最终可用性仍在实际位置验证。

原始输出、退出结果、实际变化和不确定性直接落盘并提供给评审。主助手的摘要不是唯一证据。检查器首先用少量正确、错误、合法替代和缺证据样例校准，具体四例见 07；记录每位评审及整体门的误放行、误阻断和未决结果。程序已拒绝时，评审可单独离线评分以观察自身判断，但该分数不能覆盖机器失败。不扩展成通用攻击测试项目。

## R07 · 安装与整套能力激活

能力快照包括：可发现目录、已选 Skill 说明及资源版本、工具 schema、实际执行 handler/命令绑定、相关依赖环境和执行配置。模型请求及由它产生的工具调用必须引用同一快照。

### 发布顺序：先指定候选试用，再成为默认

本版把“在指定任务或验证会话中启用候选”和“成为普通新会话的默认版本”分开。入口可解析只证明能构建，不能直接取得默认发布资格。

1. 在专属版本位置准备内容与依赖，登记 `install_id`、候选快照和本次看到的原默认发布身份。仅安装和构建不会修改默认。优先使用独立版本的依赖环境，保留旧能力可运行的内容、依赖及必要配置；不能先原地改坏共享环境，再声称旧默认受到保护。
2. 从一致登记构建完整候选。失败则保留原因、候选资料和原默认；当前任务继续修复或等待，不发布部分更新。
3. 仅让当前任务或专门验证会话显式选用该候选，下一次模型调用的说明、schema 和执行绑定一起切换。经真实 Sitina 消费者入口，在拟交付的稳定版本位置及对应依赖中，运行本次发布必需的最小有效用例和直接相关检查。不能跳过消费者而只跑一个脚本、import 或检查文件存在。显式选择候选是验证输入，不是评审修改默认登记；仍遵守 R06 的执行范围。
4. 试用结果绑定候选内容、环境、检查方法和原始证据。实际使用通过才有发布资格；失败、效果未知或缺少必要条件均不发布。候选可继续修复，但修改内容或依赖后形成新快照并重验。试用产物可以按 R02 作为本任务成果复用，不为发布形式重做有效工作。
5. 在唯一协调入口内按下述 Journal 权威协议重读当前状态，核对仍允许发布的输入与任务状态、有效试用证据，以及预期原默认发布身份。将新的 publication_id、完整快照、原默认、候选关联、验证引用及发布后检查义务写入同一权威发布决议；提交才令逻辑默认生效，registry 随后按决议投影。无关登记变化可合并后复核；同一能力已有别的发布时重新评估，不抢回或覆盖。回执丢失先查原决议，不另造发布。
6. 发布后用**不指定候选的普通新会话**实际加载并调用，验证默认发现路径，且核对它实际选中的发布身份。发现后来发布改变了默认，按当前目标重新判断；不能把后来版本的结果记成本次候选通过，也不能据此覆盖后来发布。此检查通过仍不等于整项任务完成，全部成果要求、独立评审和交付继续按任务合同验收。

上述验证会话复用现有会话、检查和版本目录机制；首版每次更新只需处理一个候选，不引入多个助手并行竞争方案的平台。若旧实现无法共存，先等待占用结束，或明确报告该能力暂不可用；没有保持旧运行条件就不能承诺无缝回退。

### r4：单一权威发布决议与默认读取

按规范化 extension_root 设置一个持久共享能力 Journal 流，由已有单机协调入口管理。同一共享目录不能由不同任务各自的日志独立决定默认。任务日志可以引用共享决议，但引用补记失败不影响共享决议所含义务的存在。复用现有 Journal/CAS，不增加数据库、消息平台或另一个后台。

一次发布先持久保存完整候选及试用证据，再提交一条 CapabilityPublicationCommitted 决议。决议至少包含：稳定 request_id／publication_id、来源 task_id 与本次执行身份、已核对输入位置和目标版本、capability_id、预期旧发布身份及共享流版本、新快照与环境引用、候选／试用关联、检查方法版本及普通新会话检查义务。检查 obligation_id 由发布身份、义务类型、处理版本确定；默认和义务同属于该决议，不在提交后另向内存排队。

发布资格核对与 append 在同一短协调区完成，使用预期共享流版本；用户输入和其他发布不能穿过该区改变已核对条件。不得在持久提交期间释放协调权后直接采用先前检查；长期试用和模型判断在区外。内容引用先可持久读回，决议提交失败不令默认生效。

| 顺序／中断位置 | 权威事实与恢复动作 |
|---|---|
| 决议提交前 | 仍是原默认；不从候选目录或半写登记推断发布。恢复后核对输入与试用，再决定是否提交原逻辑请求。 |
| 决议已提交，registry 尚未更新 | 新逻辑默认、候选关联和检查义务已同时存在；重建投影及义务。可显示“已提交，等待登记载入”，不能返回“未发布”后换 ID 重发。 |
| 投影更新后，回执返回前 | 重试先按 request_id／publication_id 查询原决议并返回同一结果；不产生第二次发布或义务。 |

已安装内容与候选登记也由该流的事实事件表达，不能直接向投影添加权威安装记录；仅准备但未登记的目录可按 R08 探测恢复，不自行成为默认。

registry.json 及内存目录是共享流的可重建投影，带所属流、applied_frontier 与投影 schema 版本；generation 从应用的权威决议派生。发布、默认恢复／停用、隔离及其处理义务都以该共享流的相应决议为准。不得保留某个旧 CLI 直接改 active 或隔离文件的旁路；旧 audit.jsonl 只作诊断，不作为第二份提交凭证。

每次为普通新会话解析默认时，经同一协调入口取得一个明确的已提交读取位置。投影必须覆盖该位置，且默认、候选关系、隔离来自同一一致视图；落后则按已提交事件追平或明确等待登记恢复，不能沿用旧文件并声称当前默认已启用，也不能只检查“至少包含本次旧发布”。一次解析有确定读取位置，不无限追赶持续更新的最新位置。返回实际 publication_id、快照和读取位置；后续新派发仍按 R07 核对有效隔离，在途调用保留原绑定。

首版由同一投影写入口按提交顺序更新文件和内存视图。若派生计算在区外完成，替换前检查 applied_frontier 不倒退；迟到旧投影不得覆盖较新的投影。读取失败不回退为可信旧 active。缺失、损坏或不兼容投影从可验证 Journal／检查点重建；权威记录不可读取则明确阻碍，不从 registry 反向伪造已验证发布。

接新路径前明确盘点旧登记内容并做有来源的一次性导入或隔离兼容，不默默删除既有安装，也不把旧 audit 当作新试用证明。默认发布、撤回和普通读取路径必须一起迁移，不能只给旧 _save_registry 加锁。候选内容可复用，但实际启用仍须当前有效证据。

提交前取消阻止业务发布；发布已经提交后取消不撤销事实。普通新会话检查、隔离和必要默认处理从共享决议恢复，不能等待原任务日志“再记一次”或重新开启已取消业务。条件撤回同样提交新决议并投影，保持后来发布保护与发布身份不倒拨。

### 使用失败如何归因和处理

| 实际情况 | 处理 |
|---|---|
| 候选构建成功，首次真实试用失败或未知 | 保持原默认，保存候选、结果和原因；修复后重验。原来没有默认则仍为“未启用”，不能虚构一个可用旧版 |
| 输入不合适、用户凭据缺失、外部服务暂时故障 | 处理该次调用的输入或外部条件，不直接判定能力回归；候选未通过仍无发布资格 |
| 能力自身缺依赖、绑定缺失、接口不兼容，或相同有效用例在新版本失败而旧版正常 | 根据实际证据确认受影响的快照与发布，隔离其后续调用；不得把集成缺陷一概归因给用户 |
| 发布后使用失败但原因未明 | 保留“原因待核实”，按已有有限探测和无进展规则处理；不能直接当作回归撤回，也不能宣称已验证正常 |
| 已确认发布回归 | 持久记录隔离状态及“核对默认并撤回/停用”的义务，然后执行下述条件处理；不能只返回原任务无限修复 |

归因由主助手提出，程序核对可直接判定的依据；有争议时使用已有独立复核。不得由报错关键词直接决定撤回。成功试用覆盖的是已声明的使用条件，不承诺此版本适用于任意输入和永远不出错。

### 默认撤回只处理本次发布

发布记录至少能查到：`capability_id`、`publication_id`、本次快照、原默认快照及其发布身份、试用/发布后验证引用、失败依据和处理义务状态。

确认回归后，故障依据、受影响发布/快照的隔离状态与默认处理义务先经既有持久入口保存。已发布能力默认按 `publication_id` 隔离，并绑定其快照和失败条件；不能因版本名或内容名相同就连带禁用后来发布。确需扩大到其他发布，须另记相应证据与适用性判断。发布前候选的限制则关联候选快照和试用身份。普通会话选择默认、活动任务派发新调用时都核对有效隔离状态，不能只读旧 active 路径。恢复先重建这些记录，再允许受影响能力的新调用；实际登记修改使用 R05、R08，不另建第二套事务机制。

协调入口从已追平的权威共享状态比较当前默认的 **publication_id 和快照**，默认处理结果提交为新决议后投影：

- 仍是本次发布，且旧内容、依赖及必要配置仍有当前可用依据：只恢复本能力的旧默认，并记录撤回处理完成。
- 仍是本次发布，但没有旧版或旧运行条件已失效：去掉坏默认，明确“该能力暂不可用”，保留修复入口；不能宣称已经恢复。
- 已经是后来发布：保留它，只记录本次撤回已被后续发布取代。即便版本名相同，也不能用旧发布的失败结果直接撤回后来发布；是否有新问题另依其证据处理。
- 提交或登记更新结果未知：先重读权威决议及其发布身份，再追平投影；尚不能处理时保留待办与隔离状态，不能盲目恢复整张旧登记表。

恢复旧快照也产生新的 `publication_id`，旧发布身份只作为来源保留，不能原样倒拨；停用写入带新变更身份的空默认记录。这样旧的迟到撤回不会再次匹配恢复后的当前状态。新默认检查或处理义务都关联实际产生的这次变更身份。

只隔离受影响的版本/发布，不删除候选和失败证据，也不悄悄替换活动任务正在使用的完整快照。已经运行的操作按 R04/R08 核实和处理；旧请求不能被新 schema 重新解释。

### 取消、重启与任务边界

- 发布前收到取消：停止新业务动作，处理已经运行的试用；迟到的通过结果不能再发布默认。未通过候选不进入普通新会话。
- 发布后只取消出图等业务目标：不自动撤回已验证正常的安装，也不继续被取消的业务任务。
- 发布后的普通新会话检查，以及检查失败后尚未完成的归因，同样持久关联本次发布，不因业务取消或退出漏做。只核实已发生的发布是否有效；依既有有限检查/重试规则形成通过、确认回归或明确待处理状态，不继续取消的出图目标，也不无限排查。
- 已确认回归所产生的隔离、默认撤回/停用义务，不随业务任务取消或重启而丢失；按发布记录恢复并条件处理。迟到失败若揭示仍有关联的发布问题，可以记录处理义务，不能重开已取消的业务循环。
- 后台退出后以已提交的试用、发布和隔离记录为准。默认发布未提交就不生效；已提交但回执缺失先核实。未知试用效果先按 R08 处理，不自动补成通过。

后台记忆整理不自动替换活动任务依赖。当前任务明确安装或更新可以采用新版本；其他来源变更由任务在轮边界明确采纳并记录。未完成操作保留所需旧内容与环境，不能提前清理。

已安装、候选局部激活、候选试用通过、默认已发布、发布已撤回/停用以及整项任务完成分别记录。构建失败或首次试用失败都不能改变普通新会话的默认；不能沿用安装器立即改 active 的行为，却只在内存回退当前任务。

目录可见而执行绑定仍旧、schema 新而说明旧，都属于激活未完成，不能归因成模型不会用工具。格式兼容仍按通用 Skill 方案，并保留旧格式入口。

### r3：候选试用身份衔接发布身份

发布记录必须持久关联候选快照、候选试用选择及本次 publication_id。原任务发布后继续使用同一能力时，下一次相关派发前登记该发布来源并核对有效隔离；不能仍用“显式候选”身份绕开本次发布已经确认的故障。发布前在途调用保留原身份，其结果按原归属处理；切换不重解释已经发出的参数。

限制依据绑定实际快照、运行条件和被证实的故障范围。改一个候选编号或选择方式不消除已知故障，修复需要新内容或新的运行条件及有效验证。后来的独立发布不因同名被连带隔离，扩大范围仍需对应证据。恢复从持久发布关系重建这一关联，不能只存在模型上下文中。

## R08 · 操作效果未知的恢复矩阵

状态至少分为：未派发、执行中、确认成功、确认失败、部分完成、效果未知。记录操作身份、执行前依据、预期影响及资源归属后才派发；重试有自己的物理尝试记录，并关联原逻辑操作，不能靠新 ID 隐藏重复。

| 操作 | 首先核实 | 可以重试的条件 | 部分完成或无法核实时 |
|---|---|---|---|
| 只读读取与查询 | 数据版本及该调用确实无外部写入 | 仍是只读、可重新获取 | 新结果标新观察时点，不补造旧结果 |
| 文件创建/替换/补丁 | 当前内容、执行前内容、预期结果 | 重新获得写入权后核对当前前置条件，派发仍属于该执行段 | 已为预期结果则补记；第三种内容先核对差异，不覆盖用户修改 |
| 追加/改名/删除 | 源与目标身份、预期出现或消失的内容 | 能证明尚未执行且前提未变 | 不重复追加；不凭单一文件缺失认定整项操作成功；不能恢复并覆盖用户后续编辑 |
| 下载/Git 获取 | 本任务目标目录、版本和完整性 | 支持续传，或可重建任务自己的 staging | 完整成果复用，部分成果续传或重取；不清理用户原目录 |
| 依赖安装 | 环境身份、旧进程、实际版本与最小运行 | 旧写入者已停，安装器在该环境可安全重跑 | 修复或重建任务拥有的环境；共享环境不整体回滚；额外安装脚本效果不明时报告卡点 |
| 长命令/构建/出图 | 启动身份、完成记录、日志与产物 | 原操作已结束且已知可重跑或有恢复点 | 活跃就等；缺退出码时查产物，不能把 PID 消失当成功或未执行 |
| 扩展内容与登记 | install_id、候选试用、权威发布决议、默认／隔离与投影位置 | 完整内容可复用，先按原请求查决议，再按当前发布身份条件处理 | 已提交只追平投影和义务；仅候选准备好则继续试用，不自动发布；回归按 R07 新决议处理，不恢复整张旧表 |
| 运行检查 | 对象、检查环境、原操作和结果 | 当前对象仍适用且检查可重复 | 对象变了重查；产生临时输出不等于验收通过 |
| 实际接入的远程写工具 | 服务查询结果、操作 ID 或幂等机制 | 服务支持相同逻辑操作重试，或能证实尚未发生 | 无可靠查询且不知能否重试时停止重复发送，保存未知结果并请求必要判断 |

每个首版可写工具接入时必须给出：`probe`（如何探测）、`retry`（何时安全）、`partial`（如何处理部分成功）、`cancel`（如何停止及剩余义务）、`unknown_exit`（无法判断时的出口）。这些是需补入工具适配的行为，不是声称已有同名函数。

每个长操作还必须登记本次调用的超时或最迟重新判断时点，以及其停止/恢复办法。查询成功、进程仍存活不允许无限等待：到期后核对阶段成果和工具语义，按原合同停止、恢复，或基于目标相关证据明确延长一次等待并保存新时点。不能仅凭 PID 存活反复顺延；没有足够依据继续等待时转为明确阻碍或请求用户决定。无日志本身不是失败，这限制的是单个操作没有解释的悬挂，不是任务总时长。到期终止造成的部分效果仍按本表处理。

已知正在运行的操作以事件或适当轮询等待，不计为失败尝试。探测本身失败按 R11 的有限暂时故障重试；工具从来不支持可靠查询时，立即说明无法核实，不无限轮询。无法安全重试就进入 `WAITING_INPUT/RECOVERY_BLOCKED`，保留实际完成部分、未知影响、选项利弊及推荐。

不承诺任意工具都可回滚或恰好执行一次。任务取消后，恢复探测和资源清理仍是需要完成的义务，但不得以清理为名继续被取消的业务目标。

## R09 · 终态与经验、交付义务的持久衔接

首版选用一个已提交 `TaskTerminated` 事件作为任务终态和后处理义务的共同来源，避免“先记成功、再在内存入队”的窗口。该事件包含终态、最终成果引用、`processor_version` 及所需义务类型；待办列表只是它的可重建投影。

`obligation_id = terminal_event_id + obligation_type + processor_version`。启动及后台处理时重建“终态已存在而义务尚未完成”的列表。成功、最终失败、取消产生结项整理义务；等待、卡住、暂停不产生最终经验。

经验处理可以重复计算，但提交采用同一逻辑义务身份去重。写候选、独立审核和 accepted 发布都关联来源义务及版本，完成记录能重建。提取者崩溃或审核调用故障只重试未完成整理，不重新运行用户任务，也不自动把未审核候选视为有效事实。

单条候选区分“已发布／已合并”“明确拒绝／无需形成条目”“等待审核或重试”“需要处理”。父整理义务按下述完整清单汇总结算，不能因其中一条发布或拒绝就完成。完整有效空清单可结清为无需经验；重启不重复处理已结清项。只有调用故障等可恢复问题重试；拒绝后重新提案须有修订及新依据，不无限再生成同一候选。

本地交付通常是成果已持久保存并在结果入口可查。可选通知失败作为独立义务补发；用户明确要求的外部交付仍属任务验收，未完成时保持 `VERIFIED_PENDING_DELIVERY`，不能提前成功。实际远程发送若效果未知，按 R08 核实，不承诺通知绝无重复。

日志中的完整终态事件不可读或未提交时，不能靠另一个摘要文件宣称成功。成果文件已写好但终态提交失败，恢复后可重新验证并条件提交；不是重做全部工作。

### r4：完整候选清单与逐项结算

首版选择“完整提取清单先提交，候选独立处理，父义务汇总”。父 obligation_id 不变；记录来源范围、提取版本、当前有效提取请求及 batch_id。完整提取结束后，先持久保存各候选内容，再经唯一入口条件提交不可变清单，包含 candidate_id、内容引用与来源。候选身份在同一清单内稳定，不单凭 conflict_key 代替，也不能靠重命名另起重试计数。

清单提交前不发布任何候选。提取中断或部分响应只作恢复材料，不是完整清单或“无需经验”；可以续接或重做尚未完成提取，迟到结果只允许当前有效提取请求提交。清单已提交后先读回原清单，不因回执丢失重新生成另一组候选。只有完整有效的空清单能直接结清父义务。

每条候选记录其修订、审核请求、相关记忆版本、处置及重试次数／next_due_at。发布／合并决议同时指明本次已结清的 candidate_id 和父／清单身份；明确拒绝或无需条目也以持久处置记录结清。审核通过但尚未发布、调用超时、事实争议或需要处理都未结清；隔离不自动表示审核已完成。

父义务仅在“完整清单已提交，清单内全部候选有最终处置”时完成；汇总可由清单和各处置事件重建。可显示“发布 1、拒绝 1、待处理 1”，此时仍未完成。最后一条决议已提交、父汇总未写即退出，恢复直接重建完成，不重新提取或发布。

重试只处理未结清项：A 已发布不再发布，B 被拒绝不因 C 超时重提；C 耗尽既有有限重试后保留需要处理，不谎称整体完成，也不重跑用户任务或阻止新任务。新依据导致候选修订时显式关联原身份与旧处置，旧修订的迟到回执不得结清新修订。完整父义务已结束后，确需再提取则建立有理由的关联后续义务，不重开旧清单或删除旧结论。

### B7 · 终态经验的历史输入证据契约

经验提取和独立审核只能使用由真实终态历史核实的 `input_evidence`：按原 task 的 Journal 顺序重放到终态 Envelope，绑定原 task/session、run/epoch、goal／acceptance 版本、终态身份与 `handled_input_seq`，再逐条读取原 CAS body 并校验引用、哈希、task/input/kind 身份。终态之后的输入、尚未处理的输入、缺失或错序输入不得混入；无法完整核实时在 Provider 派发前停靠，保留可追溯原因且发送计数必须为零。

候选审核的来源读取／原生审核绑定也必须处于持久化前检协议内。证据缺失、不可读、格式／身份错误或超预算且尚未发送时，以 candidate/revision/source closure/request/attempt 绑定的处置记录原因、exact send=0、not_sent 与 next_due_at。当前首版复用候选处理最多三次的总预算；该计数不是 Provider 发送次数，物理发送事实另外保存。前两次 NEEDS_WORK，到期后可续接，第三次 FAILED_FINAL 并结清该候选；所有候选明确处置后才 SETTLED 父义务。审核身份包含候选尝试序号，同一 Host 请求 stem 不造成不同尝试身份冲突。未到 due 不再读取或派发，重开继承状态。写入这些处置本身失败仍传播并 fence，不能伪造持久成功。

证据最多 128 条、单条正文最多 16 KiB、投影总量最多 48 KiB。原始 goal 是目标基线；已处理的 `MESSAGE`／`CORRECTION` 是本任务语义输入；`PAUSE`／`CANCEL`／`STATUS` 等控制输入只标记为 control-only，不自动升级为长期偏好。候选可声明 task-specific 或 reusable 适用范围；task-specific 条件必须非空，并且条件要保留在最终可召回的 memory 正文或既有字段中。候选引用的输入序列可以为空（允许仅依据原 goal 与实际终态结果），非空时必须是已核实的语义输入，不能引用控制、未来或不存在的序列。

这是一项来源和范围约束，不是“模型绝不会泛化”的保证；不支持的普遍规则仍须由审核拒绝或要求补证。旧 source closure、旧 CAS 哈希、历史 manifest 和没有新增可选字段的旧候选继续按原格式读取，不按本契约悄悄重算或改写。

### r3：经验生效、审核提交和调度机会

新任务记录 memory_view_ref（可用审核经验的发布位置或版本集），采用的条目另记 ID、版本及来源。结项新增或改进的普通经验默认供后续新任务使用，不静默替换活动任务的方法依据。活动任务仍能查询原始历史，结果作为带来源的证据；用户当前纠正按 R02 立即处理。已被确认错误、撤销或隔离的条目不得因固定旧视图继续当作有效事实，下一次依赖它的行动前排除并重新取证。撤销影响已采用证据时重新核对相关结论，不机械重跑所有成果。

候选审核绑定来源与相关 conflict_key 的当前版本。发布时由同一状态入口核对审核所依据的相关版本：不相关变化可以合并，相关变化只重做受影响的冲突／适用性核对；未明时保持 disputed。不得用迟到审核重新启用用户已撤销的事实。accepted 发布、旧版本替代及对应单条候选处置由同一个持久记忆决议事件表达，父义务按已提交清单汇总重建；不靠两次独立文件写入维持一致，也不在模型审核期间持锁。

后台启动扫描及后续处理按 next_due_at 安排已有义务。每次可调度边界检查到期待办；首版给予一个可配置的后台处理名额，不能只在所有用户任务结束后的空闲期运行。状态控制与必要效果收尾优先；提取和独立审核在短提交之外运行，无需新服务。需要工具产生效果时遵守其声明范围与 R05。记录重试原因、下次时间、最老待办年龄；无有用经验或审核拒绝可结清。下一任务不必等待经验整理，报告可说明相关经验仍在处理中，不谎称已经生效。

## R10 · 上下文容量与持久历史

完整失败记录、原始证据和历史要求持久保存；每次模型请求只装入有界表示。常驻当前目标与硬约束、当前验收条目摘要、未解决义务、当前阻碍、关键已排除方法索引。较早细节、完整失败正文和长输出保留可寻址入口。

构造请求时按实际模型计算系统说明、工具 schema、任务状态、近期结果、摘要、检索和协议包装；预留模型输出及下一次工具结果处理空间。大工具结果先落盘，返回有界摘要/状态/读取入口，不能把任意 stdout 全塞进下一轮。

超过容量时顺序处理：缩减无关检索和旧对话 → 压缩可压缩描述并核对关键要求 → 用任务记录生成确定性的简表与引用目录。摘要生成失败不覆盖原始记录，可暂用已验证简表继续。

硬约束本身过多时不得静默删掉。先把当前执行单元缩小，只载入其完整适用约束，并保留全局要求索引；无法确保覆盖时进入 `CONTEXT_BLOCKED`，保存任务并说明具体缺口，需要时请求必要拆分。它不是任务失败或四次无进展，不增加全任务轮数上限。

旧 20/20/15/10/10/25 百分比不作为必须满足的硬比例。当前输入和不可缺少规则也要计数；“pinned”表示不能丢持久语义，不能解释为每轮无限注入。检索入口与文件引用必须可实际读取，失效时明确标记并补证据。

## R11 · 尝试、进展与各类计数

一次尝试关联 `attempt_id`、验收项、稳定 `blocker_id`、要验证的假设或要达成的结果、实际动作/完成提案、结果和证据。相关多次读取或工具调用可以组成一次调查尝试；同一工具调用的传输重试不伪装成多个新的业务策略。

派发前登记本次问题、有限动作或调查批次及结束条件，批次结果齐备后必须结算。不能在没有新依据时向同一批次追加重复读取来无限延期；需继续调查时先结算本批次的证据与进展，再建立有关联的后续尝试。等待真实操作可暂不结算，但必须关联具体操作并遵守 R08 的重新判断时点。结算以调查问题和证据为单位，不改成四个工具调用即停。

主助手提出归属与进展解释，程序保存身份并核对直接事实。给同一障碍改名、换参数拼写、重新启动不能直接清零。拆分/合并障碍保存来源关系和未解决尝试；拆分时仍继承相关未解决历史，不能制造空计数器。

| 计数 | 增加条件 | 清零与恢复 | 达到边界 |
|---|---|---|---|
| 行动无进展 | 一次有意义尝试结束，未带来与当前阻碍有关的有效新证据或改善；重复无证据完成申请也归入原缺口 | 确认进展只重置对应阻碍的连续计数；重启、改名和暂停不重置 | 连续四次进入 `STALLED`，汇报并等待新信息或方向 |
| 评审分歧 | 对同一要求与问题反复提交，出现相同未解决分歧，没有新的解决依据 | 问题被证据解决或当前要求实质改变后建立新记录；旧争议保留 | 三次集中展示分歧、证据和建议；不自动通过 |
| 暂时调用故障 | 同一物理调用/探测的可重试故障，如传输失败；不包括真实正在运行 | 成功得到有效响应后结束该重试组；恢复保留次数 | 首版建议默认初次失败后最多重试两次，按调用配置设置间隔/超时；耗尽进入等待服务或明确阻碍，不能无限另起 ID |

最后一项是本轮可配置的工程默认值，不是用户“四次”的延伸，也不是任务总预算。正常下载进度与等待结果不进入故障重试计数。评审内容分歧和评审服务不可用不混算。

进展可以是验收项推进、取得必要事实、排除关键原因或解除依赖；新文字、重复引用、与目标无关的发现不是进展。程序核对引用存在、对象适用性和证据是否重复；语义相关性仍由助手判断。需要凭存疑语义清零时做一次定向独立核对，未判明之前不清零、不派生同一障碍的新尝试。复核后仍无法判断时记录争议并进入 `WAITING_INPUT`，说明完成部分、证据缺口、选项与推荐；不自动发起第二条同问题复核链。收到新证据或用户决定后再继续。

从 STALLED 恢复必须记录解除原因：新的信息、环境变化、用户选定新方向或明确授权继续当前尝试。保留旧计数及新尝试段的关联；“继续”不是删除历史，旧失败方法仍可检索。

### 2026-09-08：T1—T7 终止机制补强

**T1 · 有限调查批次必须实际归还调度器。** 在批次业务工具派发前持久登记 `attempt_id`、当前任务／执行／输入版本、验收项、稳定问题及阻碍来源、有限调查范围与结束条件。不能仅在整个 `runtime.run()` 返回后才补造尝试身份。运行器在完成已登记批次、检测到无新依据的重复动作、控制变化或明确调用故障时，返回结构化结算信号；后续调查先结算旧批次，再建立有关联的新批次。可以用显式的单批工作额度保证归还调度器，但额度用尽只意味着本批次让出，不代表全任务失败，也不等价于四个工具调用。满足目标的长调查和超过四次的有效工具调用仍可继续。

重复证据按适用验收项、逻辑动作、对象版本、规范化参数／页范围、内容或结果语义判定。新调用 ID、时间戳、序列化包装、新文字和重复读取的成功状态均不单独证明进展。规范化不得合并确有语义差异的参数或不同分页。新来源及新内容需要与本次问题有关；存疑进展沿用本节一次定向核对与明确等待的出口。真实操作等待必须绑定操作和重新判断时点；等待不制造业务失败尝试，同一结果不能被无限轮询并宣称新证据。

**T2 · 历史进展与当前有效成果分开。** 同一适用验收项及阻碍保存已见有效状态、证据及退步记录。`A → A+B → A → A+B` 的第二次 A+B 只是恢复旧水平，不能再次清零无进展计数。新满足项、以前未获得的必要证据、首次排除的关键原因或可验证的相关环境变化可以形成进展；不能只与最近一次比较，也不能把历史上曾满足的项目当作当前仍然满足。与原问题无关的修改不得清零。恢复、拆分、改名和重新委派保留相关历史血缘；确有用户新方向或条件改变时明确记录新的适用范围及恢复依据。

**T3 · 按稳定问题管理独立复查。** 新复查协议结构化返回当前验收项、具体问题、被审对象、证据及处置；稳定问题身份由程序登记并核对关联，不能信任模型每次任意换一个 ID。新缺口、同一未解决缺口的重述、已有缺口被证据解决，必须区分。仅对同一要求、同一问题且没有新的解决依据的完整复查增加三次分歧计数。先后解决 A、B、C 不能误记为同一问题三次；相同 A 换说法、换 ID 或做无关编辑也不能清零。

复查格式无效、必需证据未成功读取、实质内容争议与 Provider 服务故障分别记录。格式或证据交付问题先在有限修复／补证组处理，不能为了修 JSON 自动安排主助手改业务代码；耗尽后明确等待。修复组不会因新 run／消息 ID 重置。未知旧复查格式不能凭空补成精确问题身份或自动 PASS。必要评审及实际读取证据门仍保留，新增返回协议同步 prompt、parser、持久记录与测试；仅修提示词不算完成。

**T4 · 任务调度器统一解释停止。** 新 Loop 的内层只交付“批次完成、需后续调查、重复无进展、等待操作、调用故障、输入／控制变化”等原因及原始证据，不独立提交任务 `FAILED/SUCCEEDED`。旧三次相同工具失败分支不能作为新任务的另一套停滞器；任务级四次、同问题复查三次、调用重试分别由同一合同记录。局部额度／重复检测只能促成归还与结算，不能隐式变成默认全任务总轮数、token 或费用门。

**T5 · 通用只读委派的接入前提。** 委派必须绑定父任务与目标／输入版本、稳定委派身份、调查范围、唯一负责人、验收和结束条件、深度及结果引用。同一问题再次委派继承证据与尝试历史；换助手或委派 ID 不清零。兄弟返回父任务，依赖登记不能制造祖先互等；并发槽位限制同时运行数量，不充当全任务总预算。父任务暂停／取消或改变目标后，子任务停止相应新派发；迟到结果按旧绑定存证，不能批准新目标。父任务终态前确认必需子任务已结束、取消并结算，或完成明确交接；未结束副作用不得因子任务只读标签被忽略。本轮可实现纯合同与验证器，但必须标 `CONTRACT_ONLY`，不得据此宣称真实 spawn、取消传播或后台恢复已接入。

**T6 · 不依赖模型的停止报告。** 调度器从持久任务／操作／成果记录生成停止报告，至少含实际状态与原因、已验证完成项、当前成果和部分改动位置、未完成项、证据入口、未知效果、恢复条件、可选行动及推荐理由。当前未验证改动不能混为已验收成果，历史成果不能冒充当前交付。报告带任务与输入／成果版本并可靠关联停止事件；模型不可用时也能读回与展示。生成摘要、等待或查看状态不派发新的 Provider／业务调用，不把卡住／等待写成终态；明确取消仍受 R02/R04/R08 的效果结算约束。可选语言润色不能阻碍停止、保存或基本交付，也不能开启新的无界复盘链。

**T7 · 假进展与误停止成对验证。** 最少覆盖成功重复读取、有效长调查、参数／分页规范化、进展振荡、新事实与真实改善、同分歧改名、不同分歧依次解决、格式／证据／服务错误分离、模型不可用仍有停止报告、控制变化与迟到结果、旧事件兼容和 T5 合同校验。报告分别记录重复动作、振荡、分歧类别、让出原因和误停止样例；不以平均轮数下降替代完成率，不记录原始思考正文。真实 Provider 小样例与脚本／本地 HTTP 的边界测试分开报告；T5 未接入的真实协作保持未验证。

## R12 · 检查方法变更不能削弱验收

每项检查方法有身份与版本。变更记录包括原方法、新方法、原因、检查对象及覆盖差异；不能只保持验收文字不变。

| 变化 | 生效条件 |
|---|---|
| 路径、命令参数的等效修正 | 记录方法修订；证据对象与覆盖确实不变可简化核对，不机械作废所有验收 |
| 更换检查机制、减少覆盖、改变环境或成果对象 | 更新 `acceptance_version`，对必需要求的证明覆盖做独立复核，再决定能否采用 |
| 实际降低用户必须要求 | 保留原标准，说明完成部分、阻碍及取舍，等待用户明确接受；告知不是同意 |

“新会话中实际可用”不能从新建会话实际调用改成读安装日志；“产物内容正确”不能改成只检查文件存在。等效工具允许替换，不规定唯一正确命令。实质变更之后，旧评审与检查不得默认批准新合同，按 R02 关联和复用证据。
